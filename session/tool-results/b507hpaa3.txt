DASCONSTRAINTS (28)
 - FLOW: DAS receives data from source systems and is the only legal source for DAB. Nothing may read a source system except DAS. [the-architectural-blueprint]
 - PERSIST (absolute): 'Non-volatile. Not allowed to update or delete data.' Every load is retained so DAB and DAR can be rebuilt from full DAS history at any time. This forbids dlt write dispositions that overwrite or physically merge/delete. [the-architectural-blueprint]
 - SIMPLICITY (absolute): 'Capture and persist only. Transformation logic resides in the code that loads DAB.' Onboarding a new source must stay close to a configuration exercise. [the-architectural-blueprint]
 - METADATA (absolute): 'Every data point entering DAS has to be recorded for auditability' — from where and when. Load-level audit records alone are insufficient if a single data point cannot be traced to origin and arrival time. [the-architectural-blueprint]
 - Ingestion must NOT commit to a schema. Land the payload raw — 'everything in a big JSON blob' — because committing to a schema at ingest 'always created issues when source schema changed'. [the-work-before-the-answer]
 - Data is never lost when schemas change: an unknown or changed upstream field must still land. Schema drift is a contract-update event, not a pipeline failure. [the-rise-of-model-driven-data-engineer]
 - DAS is TWO physical stages, not one: landing zone (raw as produced, often JSON strings, no schema enforcement) and staging (unpacked to tabular, faithful to source structure). Do not collapse them into one destination table. [the-rise-of-model-driven-data-engineer]
 - 'Ingestion is forgiving (accept all data as JSON); unpacking is strict (contract-driven).' Two different validation postures in one layer. [the-rise-of-model-driven-data-engineer]
 - Staging is generated from a declarative contract, never hand-written: 'The actual SQL that produces the structured tables with unpacked data is then auto-generated by scripts that read each contract and applies the contract rules to build the SQL.' [the-work-before-the-answer]; 'A Python generator reads these contracts and produces SQLX files that Dataform executes against BigQuery.' [ai-assisted-data-engineering]
 - ACID TEST: 'is your contract documentation that someone manually keeps in sync with custom SQL, or does it directly generate unpacking logic?' A contract that only annotates hand-written SQL does not count. [the-rise-of-model-driven-data-engineer]
 - Generated SQL is disposable build output; never hand-edit it. 'Contracts are truth; SQL is artifact.' Regeneration must be idempotent. [the-rise-of-model-driven-data-engineer]
 - The DAS generator must emit, per contract: nested JSON field extraction, type casts, array handling, AND both a historized view and a latest view. [the-rise-of-model-driven-data-engineer]
 - The latest view must be a late-arriving-correction-tolerant projection over historized data — 'If sources send incorrect data then corrections, "latest" views automatically reflect the corrected state.' Not a snapshot, not first-write-wins. [the-rise-of-model-driven-data-engineer]
 - Uniformity is the point: 'every staging table will work exactly the same across all sources.' One canonical naming convention, one set of permitted logical steps, one query structure. Per-source special-casing is the eliminated anti-pattern. [the-work-before-the-answer]
 - The contract format must be structurally incapable of expressing business logic: 'The constraints are features: you can't accidentally inject business logic into pure staging.' [ai-assisted-data-engineering]
 - Contract content is four things: which raw table to read, what fields to extract, how to type-cast them, what expected values look like. [ai-assisted-data-engineering]
 - DAS output must be typed AND documented at column level; column descriptions must actually be populated in the warehouse because every agent reads INFORMATION_SCHEMA.COLUMN_FIELD_PATHS before writing SQL. [ai-assisted-data-engineering]
 - Every contract's output is validated with no opt-out — a 4-tier framework: dry-run compile syntax validation, NULL detection across millions of records (not sampled), automatic root cause analysis for extraction errors, and one unnamed fourth tier. [ai-assisted-data-engineering]
 - Historical alignment is a defensive workflow: 'always querying actual data distributions before assuming compatibility, never trusting naming consistency.' Column names matching across eras proves nothing. [ai-assisted-data-engineering]
 - Composed identifiers are a silent-failure surface: a bad composition merged two records that should have been distinct, and 'the bug had been in the DAS for weeks, invisible because nothing downstream was looking at it.' Distinctness assertions are needed in DAS. [the-work-before-the-answer]
 - Source extraction must preserve identifier CO-OCCURRENCE within a single row. Splitting identifiers across rows/tables or dropping a 'redundant' identifier column destroys the resolution mechanism; a source with no shared identifier creates duplicates by design. [integration-by-design-analytical-identifiers]
 - The Owner+Type prefix is applied where source values are turned into analytical identifiers — the worked example puts it in the READER CAST at the DAS→DAB boundary, e.g. CONCAT('G0010001', ISIN_code). Source column names are irrelevant; only the produced value matters. [integration-by-design-analytical-identifiers]
 - Format normalization is mandatory and the target format belongs to the Domain, not the source: 'A date must follow its specified format regardless of how the source system stored it.' [definitions-for-integration]
 - The attribute Definition is the acceptance test for which source field may populate it — a source field whose meaning differs (settled vs unsettled balance, with vs without accrued interest) must not land in that attribute even if names match. [definitions-for-integration]
 - A source-shaped landing layer alone is explicitly NOT integration: without Definitions you have 'just an expensive copy of source systems.' [definitions-for-integration]
 - daana-cli reads DAS via mapping YAML: per-table `batch_expression` overrides the workflow-level expression where a source table's timestamp column differs; DATE columns are cast to TIMESTAMP automatically; cross-project sources are supported; relationship-only mapping tables (FK-only junction tables) are legal with zero attributes. [daana-cli-0-7-0-release]
 - `source_table` references are validated against auto-discovered source schemas — DAS must be reachable at validation time, and typos are rejected with a closest-match suggestion. [daana-cli-0-7-0-release]
 - Validate that the chosen ingest storage format is actually pushed down by the query engine and version in use — the named failure was Parquet on S3 with an on-prem SQL Server that did not support pruning, so all data was read on ingest, 'essentially eliminating all benefits of Parquet'. [meet-lars-fredholm-principal-data-engineer-at-daana]

DABCONSTRAINTS (38)
 - FLOW (absolute): 'Data in the DAB layer can only come from the DAS layer.' No source connection, API call or external lookup may be wired into DAB. [the-architectural-blueprint]
 - PERSIST (absolute): 'Non-volatile. Not allowed to update or delete data.' Historized and append-only; any analytical number ever served must be reproducible from DAB as it stood at that time. [the-architectural-blueprint]
 - ATOMIC (absolute): 'Always has the atomic data point as the base of its semantic meaning.' No aggregation, summarization, bucketing or pre-rollup anywhere in DAB; aggregates happen only in DAB→DAR. A non-atomic DAB is named as one of two root causes of teams demanding raw data. [the-architectural-blueprint]
 - REUSABILITY (absolute): 'Produce clear, well-defined atomic business semantics without focus on analytical use-case.' If a construct only makes sense because of one downstream requirement, it belongs in DAR. [the-architectural-blueprint]
 - BUSINESS ORIENTED (absolute): 'No semantic or structural representation that is source-system specific or use-case specific.' Adding a second source for the same concept must not add a parallel structure; swapping a source out must not change any DAB structure. [the-architectural-blueprint]
 - METADATA (absolute): lineage per data point through the integration step, including WHICH business rules were applied and WHEN — not merely which DAS table it came from. Rule versions and effective times must be recoverable. [the-architectural-blueprint]
 - DAB is the stability contract for everything downstream: 'Source changes stay isolated in DAS. Business semantics stabilize in DAB.' A source renaming customerID to account_id must be absorbable entirely inside the DAS mapping, with zero model edits and zero DAR impact — a testable invariant. [why-we-built-daana, the-rise-of-model-driven-data-engineer]
 - Dependency direction is inverted: the business model is authored from business entities and source systems map toward it, never the reverse — 'production systems start converging to map against the business logic, not the other way around.' [the-work-before-the-answer]
 - DAB is ensemble-modeled: 'that's where ensemble modeling techniques earn their keep in the Data As Business (DAB) layer.' Cited lineage: Hans Hultgren, Dan Linstedt; the concrete framework named elsewhere is the Focal Framework / Focal point. Do NOT build DAB dimensionally. [why-we-built-daana, integration-by-design-analytical-identifiers]
 - The model must be declared before data flows — entity definitions come from decomposing business questions into constituent measures and dimensions, and become 'the shared vocabulary every other agent references.' [ai-assisted-data-engineering]
 - DMDL input shape: top-level `entities:` (id, name, definition, description, attributes) and `relationships:` (id, name, definition, source_entity_id, target_entity_id). Attributes carry id, name, definition, optional description, type, optional effective_timestamp, optional group. [the-rise-of-model-driven-data-engineer, why-we-built-daana]
 - A SECOND required input exists: a data-mappings declaration binding DAB attributes to DAS staging columns, timestamp handling, and multi-source merge rules. 'From these declarations and a corresponding one for data mappings, systems generate transformation logic.' Its format is never shown. [the-rise-of-model-driven-data-engineer, why-we-built-daana]
 - Joins are never hand-written: 'These relationships drive join logic in the generated views. You don't write the joins - the model does.' If a join is needed, the missing thing is a declared relationship. [why-we-built-daana]
 - Relationship cardinality is load-bearing and must be a first-class declared property — the USS generator distinguishes n:1 (safe), 1:n (fan-out) and m:n (no safe direction). [consumption-layer-generates-itself]
 - DAB must explicitly declare entities, keys, relationships, history, grain AND measures — the DAR generator has no other input to read. 'Get that layer right and everything downstream generates. Get it wrong and the generated USS will faithfully reproduce the mess.' [consumption-layer-generates-itself]
 - Budget explicit remodeling work to resolve m:n relationships into n:1 paths: 'If your domain leans hard on many-to-many, you will model around it, and that is real work.' Unresolved m:n measures fall outside generated coverage. [consumption-layer-generates-itself]
 - No hand-written historization: 'No historization code written. No SCD2 logic. No temporal join patterns. The entity definition drives everything.' History is a derived property of `effective_timestamp: true` plus the source mapping. [why-we-built-daana]
 - One historization mechanism everywhere, declared not implemented: 'Historization is something you declare, with one mechanism everywhere, rather than something each pipeline solves in its own way.' [context-isnt-enough]
 - Grain is fixed per entity and enforced by the compiler; mixed-grain tables must be structurally impossible. [context-isnt-enough]
 - Every entity gets identifiers from the start — an entity with no declared identity should not be a legal model. [context-isnt-enough]
 - Attributes are modeled as answers to atomic business questions and carry their full semantic payload: 'a loan amount is not just a number, but a number plus a currency.' DMDL expresses this with `group:` (NUMBER + UNIT members under one parent). [context-isnt-enough, the-rise-of-model-driven-data-engineer]
 - IDENTITY (IDFR pattern): analytical identifiers must be globally unique and cradle-to-grave. Business identifiers (source keys, email, phone) may never be used directly as DAB instance keys. [integration-by-design-analytical-identifiers]
 - Identifier token format `{Owner+Type code}{Value}` with FIXED-WIDTH codes (example 4+4), concatenated without a separator so collision-safety holds by construction. Every Owner and every Type must be a unique string of the same length across the system — a validation rule the tool should enforce because the runtime never will. [integration-by-design-analytical-identifiers]
 - Integration happens at DESIGN time, in DAB, as a property of the identifier: 'integration is not a transformation applied after loading.' No per-source matching rules, no manual mapping, no reconciliation at load time, no matching engine. [integration-by-design-analytical-identifiers]
 - Each multi-identifier entity gets one `{ENTITY}_idfr` table mapping many identifiers to one surrogate key. Minimum viable schema is two columns (identifier value, instance key); everything else is platform-configurable. The table must NOT be unique on the key and must NOT carry per-source or per-slot columns. [integration-by-design-analytical-identifiers]
 - Resolution matches identifier VALUES, not slot positions: five independent LEFT JOINs of the staged row against the whole `_idfr` table. 'The value creates the connection; the position is incidental.' [integration-by-design-analytical-identifiers]
 - Four separable, independently testable stages: READER → INTEGRATION → TRUEDELTA → INSERT. No stage before INSERT may write — resolution is a pure function of (incoming row, current `_idfr` snapshot). [integration-by-design-analytical-identifiers]
 - Multi-identifier resolution is OPT-IN per entity: 'For an entity with a single, stable primary key, this overhead is unjustified - the pipeline should be skipped entirely.' [integration-by-design-analytical-identifiers]
 - Onboarding a new identifier or source creates only new rows — 'no DDL change, no ALTER TABLE'. Adding a 6th slot is a code change at every stage, not a schema change. [integration-by-design-analytical-identifiers]
 - Every entity, attribute, relationship AND metric must carry a clear, business-oriented Definition accessible to humans and AI ('Semantic Clarity'). Definitions must live inside the model artifacts, not an external wiki. [definitions-for-integration]
 - Definitions are recursive: Concept → Characteristic → Domain → Value, and 'each level in the hierarchy is itself a Concept requiring its own Definition.' Attributes, domains and individual code values are first-class definable objects. [definitions-for-integration]
 - The Definition — not structural resemblance between source tables — is what authorizes merging two sources into one entity. Never integrate on name match: two systems may use different Terms for one Concept, or the same Term for different Concepts. [definitions-for-integration]
 - Value-level integration is required for completeness: 'The ability to integrate Values - not just Concepts, Characteristics, and Domains - is what completes the common information view.' Closed domains (GICS, ISO 4217) need per-value Definitions and cross-system code integration. [definitions-for-integration]
 - All DAB definitions — models, mappings, workflows, connection profiles — live in version-controlled YAML; the warehouse holds no authoritative state a rebuild would lose, and nothing may be hand-edited in the warehouse. [daana-cli-0-7-0-release]
 - Names may use any casing (0.7.0 relaxed UPPER_SNAKE_CASE) but must be valid SQL identifiers — letters, digits, underscores only, no hyphens — and short enough that generated index/table/schema names fit PostgreSQL's 63-character limit. [daana-cli-0-7-0-release]
 - Batch state is warehouse-resident in a `batch_history` table (Running → Complete / Failed); 'Failed pipelines don't advance the watermark'; stale runs auto-recover per `batch_stale_timeout` (default 8h); `--force` overrides stale detection. Local CSV batch state (~/.daana/batch/) is gone. [daana-cli-0-7-0-release]
 - Entity key columns in metadata tables are VARCHAR(256); `type_key`, `data_key`, `inst_key` and batch-lifecycle keys remain BIGINT (ADR-109). `type_key` values are read from metadata tables at Function DDL time, not from a sequential counter. [daana-cli-0-7-0-release]
 - INCREMENTAL vs FULL_LOG is a per-pipeline choice with materially different relationship semantics: INCREMENTAL uses forward-only emission with query-time set detection (no `row_st = 'N'` for set transitions); FULL_LOG soft-deletes on source-row disappearance. [daana-cli-0-7-0-release]

DARCONSTRAINTS (29)
 - FLOW (absolute, two rules): 'Data usage for analytical purposes is only allowed from the DAR layer' and 'Data in the DAR layer can only come from the DAB layer.' No BI tool, notebook, ad-hoc query, feature store or ML pipeline may touch DAS or DAB; no DAR object may read a DAS table or source. A missing attribute is a reason to add it to DAB, never to reach past DAB. [the-architectural-blueprint]
 - PERSIST: DAR is the ONLY layer permitted to be volatile — 'DAR structures may be volatile where the requirement demands it (e.g. full refreshes of aggregated views), but all changes must be traceable.' Users and auditors must understand what data was served, when, and how it was derived from DAB. [the-architectural-blueprint]
 - SPECIALIZATION: 'Data structures and data points are specialized to support the specific requirement(s).' A general-purpose 'one big model for everyone' in DAR violates the principle. [the-architectural-blueprint]
 - REQUIREMENT ORIENTED (the sharpest constraint in the corpus): 'No "reuse" between different requirements. Different user groups must not share structures even when requirements align. No intra-dependencies between requirements of different user groups.' Deliberate duplication is required, not a smell; do not factor out shared conformed dimensions or shared intermediates. Reuse belongs in DAB only. [the-architectural-blueprint]
 - METADATA: 'Every data point entering DAR has to be recorded for auditability' — tying each delivered data point to a user group, a time, and its DAB derivation. Delivery-side audit, not just build logs. [the-architectural-blueprint]
 - DAR generates itself from the business model: 'The question is not which star schema to build by hand. The question is why we are building them by hand at all.' No hand-authored consumption SQL as the primary path. [consumption-layer-generates-itself]
 - DAR is the only layer allowed to contain star/USS/OBT/mart shapes; DAB must stay free of them. [consumption-layer-generates-itself]
 - The generated USS is ONE central table — the bridge (Puppini's 'super fact') — holding all relations and all measures, not per-subject-area facts. [consumption-layer-generates-itself]
 - Stop classifying tables as facts vs dimensions: 'Every entity can play both roles - an order is a thing you measure and a thing you slice by, so is a customer, so is a product.' [consumption-layer-generates-itself]
 - The bridge grain is the MEASUREMENT EVENT, not the entity instance: one row per event, each carrying its own date (order placed → order date, shipped → shipped date, due → required date). 'One calendar, every process.' [consumption-layer-generates-itself]
 - Build rule: 'follow any path that never fans out, and inherit everything along it' — an n:1-only graph walk inheriting keys and measures. m:n edges have no safe direction, so 'the generator skips it and tells you.' Fan-out safety is a build-time invariant, not analyst discipline. [consumption-layer-generates-itself]
 - Additivity is derived and guaranteed: 'Not additive if you remember to be careful. Additive by construction, with the safe paths worked out for you.' The result must be materialized as a sliceability contract (measure × dimension matrix), not left as tribal knowledge. [consumption-layer-generates-itself]
 - The sliceability contract doubles as a pre-trust coverage report — 'you can read off exactly which questions the model answers and which it does not... Coverage is not a matter of faith' — and must be published in a vendor-neutral semantic format (e.g. OSI) any BI tool or AI agent can read. [consumption-layer-generates-itself]
 - Every other consumption format is a projection/selection of the same model, not a separate build: `data mart` = filter + peripherals; `obt` = flatten the row; `star schema` = split fact / dims; `feature table` = select per key. [consumption-layer-generates-itself]
 - The bridge must be directly PivotTable-consumable — 'A single bridge is a PivotTable's best friend' — i.e. a single wide table on one calendar, not only an API/semantic-layer surface. [consumption-layer-generates-itself]
 - Non-additive measures (ratios, distinct counts across the wrong grain) are NOT covered by generation and still need explicit human handling. [consumption-layer-generates-itself]
 - The bridge must support incremental loading by key or by updated-at, with full reload as fallback rather than norm (benchmark: ~1 billion rows reload in ~4 minutes on an F64). [consumption-layer-generates-itself]
 - DAR must be MATERIALIZED so it survives a DAB drop-and-redeploy: 'only the DAB layer rebuilds during the 10-15 minutes. DAR and downstream BI consumers don't notice anything as long as the rebuild completes within their refresh interval.' [daana-cli-0-7-0-release]
 - The DAR incremental predicate is `WHERE ver_tmstp > last_run_tmstp` (system load time), NOT a predicate on `eff_tmstp` (business time) — BigQuery cluster keys are tuned for exactly this. DAR must persist its own `last_run_tmstp` watermark. [daana-cli-0-7-0-release]
 - All framework column names and table suffixes are LOWERCASE as of 0.7.0 (breaking): eff_tmstp, ver_tmstp, type_key, data_key, inst_key, row_st, inst_row_key, popln_tmstp; _idfr, _desc, _x. Every DAR template referencing them in uppercase must be audited. [daana-cli-0-7-0-release]
 - `view_<source>_has_<target>` returns SET semantics (active member set at latest effective timestamp), not one row per pair. Any pre-0.7.0 row-count baseline is invalid, and DAR must not detect membership change by reading `row_st = 'N'` under INCREMENTAL. [daana-cli-0-7-0-release]
 - Pick the DAR source per use case: `view_<entity>_hist` gives one row per value-run (gaps-and-islands compaction, COUNT/AVG/SUM count value-states) while `<entity>_desc` gives every ingest observation. A fact built on `_hist` cannot answer 'how many times was this loaded'. [daana-cli-0-7-0-release]
 - DAR joins only on `{ENTITY}_key`; the `_idfr` table is an integration mechanism, not a reporting dimension. 'Downstream tables see the result, not the resolution.' [integration-by-design-analytical-identifiers]
 - DAR contains no first-time business logic: 'DAR optimizations shouldn't leak business logic.' It only reshapes and aggregates semantics defined in DAB. [the-rise-of-model-driven-data-engineer]
 - A metric is declared once with calculation, filter/qualifier, grain and dimensions, and drives three consumers from one definition: warehouse SQL, API responses, and documentation. Maintaining separate SQL per consumer is explicitly rejected. [the-rise-of-model-driven-data-engineer]
 - Consumption patterns in DAR must evolve without touching upstream layers — if a new report forces a DAB or DAS change, the layering has been violated. [why-we-built-daana]
 - DAR (Kimball framing) carries four checkable obligations: declared grain (as an explicit column tuple, e.g. `grain (order_key, fact_ts)`), conformed dimensions, additive measures, and point-in-time correctness — with a mandatory, non-skippable 5-test protocol per object and per-column nullability semantics stated with their business reason. [ai-assisted-data-engineering]
 - Optimize the serving layer for question→entity mapping, not for SQL-generation ergonomics: 'the hard part is mapping a user's question to the right entities in the data model; once that works, writing the SQL is easy.' [context-isnt-enough]
 - The semantic layer must be exposed FROM the same declarations rather than maintained on the side, and reachable by agents over MCP so non-SQL stakeholders get reproducible answers without a data-team reviewer in the loop. [context-isnt-enough, the-work-before-the-answer]

CROSSCUTTING (33)
 - ONE-DIRECTIONAL FLOW, three absolute rules with documented reasons: usage only from DAR; DAR only from DAB; DAB only from DAS. 'These are the rules the gatekeeper enforces - the absolutes we measure every deviation against.' [the-architectural-blueprint]
 - Each inter-layer movement does exactly ONE job — ingest (source→DAS), integrate (DAS→DAB), specialize (DAB→DAR). Code that ingests-and-integrates, or integrates-and-shapes-for-a-report, collapses layers and is disallowed. [the-architectural-blueprint]
 - The blueprint contains NO exceptions and NO pre-authorized bypass: 'if we do not have an absolute principle that is described - why we have it, what effect it has - we have nothing to break.' Do not build configurable escape hatches, exception flags or 'bypass DAB' modes into the platform or its docs. [the-architectural-blueprint]
 - There is no ML/AI raw-data carve-out. ML consumes DAR like every other requirement; missing inputs are added to DAB first. The named counter-example clause ('Machine Learning applications are allowed to use raw data...') is given as the exception that 'removes the mandate'. [the-architectural-blueprint]
 - Deviations are costed, not blocked: 'we do not argue with the reality, we define the cost that the reality wants to impose on us.' Record which principle breaks, why, how, the effect on maintainability/scalability/adaptability/time-to-market, the reusability lost, and the life-cycle cost — with product owner, requirement owner, DW architect and data engineer all party to the decision. [the-architectural-blueprint]
 - The vision every design decision is judged against: Maintainable, Scalable, Adaptable, Good time to market — 'throughout its whole life cycle', estimated at 15-25 years. Speed is explicitly NOT the top criterion: 'Not the fastest way, but always within acceptable timing.' [the-architectural-blueprint]
 - The blueprint is technology-free and overarching; tooling, modeling technique and process live in subordinate documents that must each be justified against the vision. Any tool (dlt, daana-cli, the USS, the warehouse engine) must be replaceable without invalidating the blueprint. [the-architectural-blueprint]
 - The declaration is the source of truth and the warehouse is an OUTPUT: 'The declared model is the source and the warehouse is an output.' No hand-edits to deployed objects; no round-tripping fixes back from the warehouse into the model. [context-isnt-enough]
 - Definitions ARE the implementation: 'the definition is the implementation. The platform reads those definitions and turns them into the running system. Change a definition, change the system.' There must be no second documentation surface that can drift. [the-work-before-the-answer, context-isnt-enough]
 - The same declarations serve triple duty — what humans read, what LLMs read, and what drives transformation generation: 'These aren't three separate artifacts that can drift - they're the same source.' [why-we-built-daana]
 - 'Naming is uniform because it is generated.' Naming rules live in the compiler, not in style guides each engineer applies. [context-isnt-enough]
 - 'Logic is defined once and compiled wherever it is needed, and nothing deployed can be orphaned, because everything derives from the current model.' Deployment is a complete projection of the current model. [context-isnt-enough]
 - Generation guarantees consistency, NOT correctness: 'A generated platform still inherits the quality of its source systems, and a poorly chosen model compiles just as reliably as a good one.' Modeling judgment and source quality still need human review. [context-isnt-enough]
 - 'A rule the agent has to remember is weaker than a rule the platform enforces.' Whenever a constraint is expressible in the model, express it there rather than in agent instructions, skills or rules files. [context-isnt-enough]
 - 'Context can route an agent to the right answer only if the platform contains a right answer to route to.' Resolve duplicate/near-duplicate definitions in the model rather than routing around them downstream. [context-isnt-enough]
 - Uniformity is an agent-facing FEATURE: 'an agent that learns the shape of one entity knows the shape of all of them.' Per-entity special cases, escape hatches and bespoke overrides erode the property that makes the platform navigable. [context-isnt-enough]
 - The platform must be re-readable as an agent recovery mechanism: semantic model + contracts + column descriptions must be sufficient to fully re-orient an agent with zero conversation history. Nothing load-bearing may live only in chat. [ai-assisted-data-engineering]
 - 'Verify before you generate' is encoded in every agent's workflow, not offered as advice: check INFORMATION_SCHEMA.COLUMN_FIELD_PATHS for column descriptions, read the view definitions, understand what's upstream — before writing SQL. [ai-assisted-data-engineering]
 - Layer boundaries are 'semantic checkpoints' that tell humans and agents what kind of work belongs where; work must be refusable at the wrong layer. [ai-assisted-data-engineering]
 - Layer names encode PURPOSE, not position or quality grade — deliberately not bronze/silver/gold or staging/core/marts, because 'ask three people what belongs in silver and you'll get four answers.' 'That distinction matters when the names are also your principles.' [the-architectural-blueprint, why-we-built-daana, the-rise-of-model-driven-data-engineer, ai-assisted-data-engineering]
 - The DW's primary job is Information Integration — 'creating a shared view of information that works regardless of where the data originated' — not storage, performance, or dashboards. Both halves are required: model integration (structure) and semantic integration (meaning). Generating a star schema is model integration only. [definitions-for-integration]
 - Acceptance scope is metadata: 'A Definition created for a single division cannot serve as an Enterprise Definition.' The scope a deliverable is advertised at must not exceed the scope of the Definitions behind it. [definitions-for-integration]
 - Build the entire stack THIN first: 'A skeleton at every layer that someone can look at, even if it's wrong. Then iterate against existing trusted reports where possible. Depth comes after the loop closes.' Depth-first on DAS cost ~six weeks and hid a silent identifier collision. [the-work-before-the-answer]
 - Three agent-friendliness requirements for the whole platform: clear semantic definitions (agents cannot intuit from context), explicit rules and boundaries (what's allowed / forbidden / requires approval), and documented processes rather than tribal knowledge. [designing-for-agentic-experience]
 - Two-tier alignment: 'harder' metadata (data contracts, entity definitions) enforces structure mechanically; 'softer' conventions (naming, SQL style) are enforced by a doc-reading agent in CI. [stop-being-naming-convention-police]
 - Model-level validation runs BEFORE code generation, not as SQL tests after deployment; and the entity definitions must live in a queryable model registry that actively drives generation, 'not documentation sites'. [the-rise-of-model-driven-data-engineer]
 - Access model: domain teams get write access to model/contract files only, not arbitrary SQL against production; the central platform team owns patterns, standards and the generation framework. Contract ownership sits with the data-producing product team as the unit of accountability. [the-rise-of-model-driven-data-engineer, the-work-before-the-answer]
 - Tested/target platforms are PostgreSQL and BigQuery; MSSQL and Oracle fail fast with 'not yet supported' at every entry point (previously they fell through to the PostgreSQL executor and produced corruption) but stay authorable in connection profiles via `PlannedDialects`. [daana-cli-0-7-0-release]
 - Declarative is NOT universally better: imperative still wins for one-off analyses, genuinely novel algorithms, performance-critical optimization, early-stage exploration, and very small teams ('three sources, ten entities, one data engineer'). Mature platforms carry both. [the-rise-of-model-driven-data-engineer]
 - Budget weeks-to-months of upfront investment (framework setup, code generation tooling, team training) before the first generated pipeline pays off. Technical debt shifts rather than disappears: the two named failure modes are over-rigid abstractions and overly generic models lacking domain specificity. [the-rise-of-model-driven-data-engineer]
 - Separation of concerns is named as the single hardest architectural decision in daana-cli: 'To make sure each part was doing its own thing and not cluttered with everything.' The user surface is deliberately skewed simple while the engine carries the complexity. [meet-peiman-khorramshahi-cto-at-daana]
 - Do not decompose the data stack with software-engineering modularity (microservices): it 'makes it very hard to solve problems around single source of truth, how to process massive data sets.' Adopt DevOps practice incrementally — 'a delicate maneuver that takes time and will be very costly if rushed.' [meet-lars-fredholm-principal-data-engineer-at-daana]
 - daana-cli is alpha software co-built with the vendor: 'The core patterns work... But translating those into a tool that works for diverse teams requires feedback.' The architectural patterns are the stable part; the tool is not. [why-we-built-daana]

NAMINGRULES (30)
 - Name the layers DAS / DAB / DAR literally in schemas, directories and docs — never bronze/silver/gold or staging/core/marts. The name is meant to carry the principle. [the-architectural-blueprint, why-we-built-daana, the-rise-of-model-driven-data-engineer]
 - DAB names must be business terms — not source table/column names, source-system prefixes, source keys, or report/use-case names. 'names should reflect business concepts, not technical implementation'. [the-architectural-blueprint, stop-being-naming-convention-police]
 - DMDL entity/attribute/relationship ids are shown as SCREAMING_SNAKE_CASE and double-quoted, with `id` and `name` holding the identical string in every example (CUSTOMER/CUSTOMER, ORDER_LINE/ORDER_LINE). [the-rise-of-model-driven-data-engineer, why-we-built-daana]
 - Entity ids are SINGULAR nouns: CUSTOMER, ORDER, ORDER_LINE, PRODUCT, SUBSCRIPTION, ACCOUNT, BASE_PLAN, INSTRUMENT. [why-we-built-daana, the-rise-of-model-driven-data-engineer]
 - Descriptive attributes are prefixed with the entity name (CUSTOMER_NAME, CUSTOMER_CITY, SUBSCRIPTION_ID, ORDER_LINE_ID); generic attributes and measures are not (STATUS, ACQUISITION_TYPE, QUANTITY, LINE_AMOUNT). [why-we-built-daana, the-rise-of-model-driven-data-engineer]
 - Relationship names are business VERB phrases read source→target: IS_FOR_PRODUCT, BELONGS_TO, BELONGS_TO_ACCOUNT, HAS_BASE_PLAN. Note both forms appear — one embeds the target noun, one does not. [why-we-built-daana, the-rise-of-model-driven-data-engineer]
 - As of daana-cli 0.7.0, entity IDs, workflow IDs, attribute names and relationship names accept ANY casing (lowercase, UPPERCASE, Mixed_Case, mixedCase); the previously enforced UPPER_SNAKE_CASE and the lint rules entity-name-casing / attribute-type-casing / relationship-name-casing were removed. [daana-cli-0-7-0-release]
 - Names must be valid SQL identifiers: letters, digits, underscores. Hyphens are no longer accepted. YAML names are preserved exactly as written; cross-reference lookups are case-insensitive at compile time; compiled output uses the model's canonical casing. [daana-cli-0-7-0-release]
 - ALL framework-generated columns are lowercase (breaking change in 0.7.0): eff_tmstp, ver_tmstp, type_key, data_key, inst_key, row_st, inst_row_key, popln_tmstp. [daana-cli-0-7-0-release]
 - ALL framework table suffixes are lowercase: `_idfr` (identifier map), `_desc` (descriptive/attribute, per-ingest grain), `_x` (relationship/cross tables). [daana-cli-0-7-0-release]
 - Generated view names in 0.7.0: `view_<entity>_hist` (one row per value-run) and `view_<source>_has_<target>` (active member set per source entity). [daana-cli-0-7-0-release]
 - Earlier posts show DIFFERENT generated-object naming: `<ENTITY>_HIST` / `<ENTITY>_LATEST` [the-rise-of-model-driven-data-engineer] and `VIEW_<ENTITY>` / `VIEW_<ENTITY>_HIST` / `VIEW_<ENTITY>_WITH_REL` [why-we-built-daana]. Treat 0.7.0 as current and the others as version drift.
 - Identifier map table: `{ENTITY}_idfr` — INSTRUMENT_idfr, CUSTOMER_idfr. Shorthand `_idfr`. [integration-by-design-analytical-identifiers]
 - Identifier slots are `IDFR_01` through `IDFR_05`; unused slots stay NULL; extending to a 6th is a code change at every stage. [integration-by-design-analytical-identifiers]
 - Surrogate key column is `{ENTITY}_key` physically (INSTRUMENT_key, customer_key) and `focal_key` generically inside the Focal Framework template — 'rename it to whatever fits your code standards.' [integration-by-design-analytical-identifiers, why-we-built-daana]
 - Owner code allocation convention (a design choice, not a system property): `G` series = global registries (G001 ISIN Organization, G002 CUSIP/ABA, G003 Bloomberg FIGI, G004 Reuters RIC); `A001`–`A999` = local systems, rolling into `B` past 999; `L` = country-specific issuers. Type codes: 0001 STOCK, 0002 CUSTOMER. [integration-by-design-analytical-identifiers]
 - USS bridge table is named `_bridge` (aliased `b`); Puppini's suggested alternative is 'super fact'. Per-entity build target is written `<entity>.bridge` (e.g. `order_line.bridge`). [consumption-layer-generates-itself]
 - USS measure columns follow `_measure__<entity>__<measure>` — `_measure` prefix, double underscore between segments, e.g. `_measure__order_line__revenue`. [consumption-layer-generates-itself]
 - USS dimension key columns follow `<entity>_key` (territory → territory_key). [consumption-layer-generates-itself]
 - DAS staging target columns are lowercase snake_case, renamed away from source casing: payload.userId → user_id, eventType → event_type, timestamp → event_ts. Note the deliberate disambiguation of a generic source name ('timestamp' → 'event_ts'). [the-rise-of-model-driven-data-engineer]
 - There are TWO casing worlds in the same platform: DMDL/DAB uses uppercase ids while DAS staging and physical columns use lowercase snake_case (YAML CUSTOMER_NAME → column customer_name). Whether this is a defined lowercasing rule or warehouse identifier folding is never stated. [why-we-built-daana, the-rise-of-model-driven-data-engineer]
 - Metric names follow `<descriptor>_<entity>_<unit>` with entities in PLURAL form: total_orders → orders_count, sum_revenue → revenue_amount. [stop-being-naming-convention-police]
 - Scope words ('total', 'sum') are forbidden in metric names because 'the semantic layer handles aggregation scope through filters'. This rule is only coherent if the semantic layer actually provides scope via filters. [stop-being-naming-convention-police]
 - Two non-regexable naming rules that must still be enforced (by a doc-reading agent): 'metric names should be self-explanatory without requiring documentation lookup' and 'names should reflect business concepts, not technical implementation'. [stop-being-naming-convention-police]
 - Source-system columns you do not control (DAS) are a legitimate EXCEPTION to naming rules: 'Is total_orders wrong because it uses a forbidden word, or is it acceptable because it's a column in a source table you don't control?' Enforcement must be layer-scoped. [stop-being-naming-convention-police]
 - Kimball/DAR naming seen in practice: `factless_fact_<entity>` (factless_fact_order), `<entity>_key` for dimension surrogate keys (order_key, base_plan_key, offer_key), `fact_ts` for the fact timestamp. [ai-assisted-data-engineering]
 - Generated index / table / schema names must fit PostgreSQL's 63-character limit — validated by the engine with a suggested fix, which bounds how long entity and attribute names may be. [daana-cli-0-7-0-release]
 - Demo warehouse schema name: `daana_dw` (e.g. FROM daana_dw.view_customer_hist). [why-we-built-daana]
 - Contract-side naming: `source_path` is a dot path into the payload; `target_name` is the emitted column; `type` and `mode` are unquoted SCREAMING_CASE (INTEGER, STRING, TIMESTAMP_MILLIS; REQUIRED). [the-rise-of-model-driven-data-engineer]
 - DMDL type vocabulary is SEMANTIC, not physical: "STRING", "NUMBER", "UNIT", "START_TIMESTAMP", "END_TIMESTAMP" — START/END_TIMESTAMP declare validity-interval roles and UNIT declares a unit-of-measure companion to a NUMBER. [the-rise-of-model-driven-data-engineer]

CONTRADICTIONS (26)
 - DAR SHAPE — the single biggest unresolved conflict. consumption-layer-generates-itself says generate a Unified Star Schema: one bridge table, 'you stop sorting tables into facts and dimensions', every entity plays both roles. ai-assisted-data-engineering says DAR is Kimball: a 'Kimball Agent' that 'builds the consumption layer - dimensions, facts, snapshots', with 'conformed dimensions' and 'additive measures'. why-we-built-daana says 'dimensional modeling remains the natural choice for the Data As Requirements (DAR) layer'. These are three different physical designs and no post reconciles them.
 - DAR REUSE — the blueprint forbids what the other DAR posts require. Blueprint: 'No "reuse" between different requirements. Different user groups must not share structures even when requirements align. No intra-dependencies between requirements of different user groups.' But ai-assisted-data-engineering mandates 'conformed dimensions' (a construct whose entire purpose is sharing structure across requirements), and consumption-layer-generates-itself makes every mart a projection/filter of ONE shared bridge, which is shared structure by construction. Deliberate duplication vs one shared model cannot both be right.
 - DAS 'CAPTURE AND PERSIST ONLY' vs CONTRACT-DRIVEN STAGING. The blueprint's DAS Simplicity principle is absolute: 'Capture and persist only. Transformation logic resides in the code that loads DAB.' But rise-of-model-driven, ai-assisted, work-before-the-answer and (by reference) contract-driven-data-transformation all put a substantial transformation step inside DAS: unpacking nested JSON, type casting, renaming camelCase→snake_case, array handling, and generating historized AND latest views. Either the blueprint's DAS is only the landing zone (and staging is unlabelled), or the staging step violates a stated absolute.
 - LAYER NAME EXPANSIONS DIFFER. 'Data According to System / Business / Requirement' [the-architectural-blueprint] vs 'Data As System sees it / Data As Business sees it / Data As Requirements needs it' [the-rise-of-model-driven-data-engineer, why-we-built-daana] vs 'Data As System / Data As Business / Data As Requirements' [ai-assisted-data-engineering] vs 'Data According to Requirements' [consumption-layer-generates-itself]. DAR is also singular 'Requirement' in the blueprint and plural elsewhere. A builder writing documentation has to pick.
 - GENERATED DAB OBJECT NAMES CONFLICT ACROSS THREE POSTS. `SUBSCRIPTION_HIST` / `SUBSCRIPTION_LATEST` (two views per entity) [the-rise-of-model-driven-data-engineer]; `VIEW_CUSTOMER` / `VIEW_CUSTOMER_HIST` / `VIEW_CUSTOMER_WITH_REL` (three views per entity) [why-we-built-daana]; `view_<entity>_hist` / `<entity>_desc` / `view_<source>_has_<target>` / `_x` / `_idfr`, all lowercase [daana-cli-0-7-0-release]. Likely version drift, but no post says which contract is current, and 0.7.0 explicitly calls the lowercase change breaking for downstream consumers.
 - CASING CONVENTION. Two posts show DMDL ids as double-quoted SCREAMING_SNAKE_CASE with id == name; 0.7.0 says UPPER_SNAKE_CASE was previously enforced, is now optional, and the three casing lint rules were REMOVED — so the platform no longer enforces the convention its own examples use. Simultaneously the DAS contract examples use lowercase snake_case target names, so the platform runs two casing worlds.
 - SNOWFLAKE SUPPORT. why-we-built-daana: 'It works on BigQuery, Snowflake, and other cloud platforms.' daana-cli-0-7-0-release: tested environments are 'latest PostgreSQL and current GCP-default BigQuery'; Snowflake appears only in the TypeTextDDL mapping and dialect-aware TRUNCATE; MSSQL and Oracle fail fast with 'not yet supported' despite having type mappings. The type-mapping table advertises dialects the engine refuses to run.
 - BUILD ORDER. rise-of-model-driven: 'Start with layers where patterns are clearest. Ingestion contracts often provide high return... Core business entities in the DAB layer offer similar benefits once you've established your domain model. Metrics definitions pay off when serving multiple consumption patterns' — a layer-at-a-time order. work-before-the-answer: building DAS 'first, in full, before we had anything end-to-end' was the ~six-week mistake; 'build the entire stack thin first.'
 - ABSTRACT-LATER vs DECLARE-FIRST. rise-of-model-driven: 'Build a few implementations, discover commonalities, then abstract. Premature abstraction before patterns emerge adds overhead without benefit.' Every other post (context-isnt-enough, why-we-built-daana, work-before-the-answer, consumption-layer) treats hand-written implementations as the failure mode and declares from day one — and daana-cli is a pre-built abstraction you adopt before discovering your own patterns.
 - ESCAPE HATCHES. rise-of-model-driven requires them ('generation frameworks that... provid[e] room for custom logic where standard patterns don't fit') while warning 'Too many escape hatches undermine consistency'. The blueprint forbids pre-authorized exceptions entirely. context-isnt-enough says per-entity special cases erode agent legibility. why-we-built-daana admits 'you sacrifice some flexibility in custom transformations' and describes no hatch at all. Four positions, no resolution.
 - IMMUTABILITY vs FULL REFRESH. Blueprint: DAS and DAB are 'Not allowed to update or delete data.' daana-cli 0.7.0 ships `--full-refresh` at workflow/entity/attribute scope, makes drop-and-redeploy of the DAB schema the standard upgrade path, and FULL_LOG pipelines soft-delete rows (`row_st = 'N'`). Rebuild-from-DAS is arguably consistent with 'reload downstream layers with all historical data', but per-attribute full refresh and soft-deletes are not obviously reconcilable with the absolute.
 - ONE HISTORIZATION MECHANISM vs PER-PIPELINE CHOICE. context-isnt-enough: 'Historization is something you declare, with one mechanism everywhere, rather than something each pipeline solves in its own way.' daana-cli-0-7-0: INCREMENTAL vs FULL_LOG is a per-pipeline choice with materially different relationship semantics (forward-only emission with query-time set detection vs. soft-delete on source-row disappearance), and the post does not say which to pick. Additionally, DAS generates historized+latest views AND DAB generates hist/latest views — two historization layers, never reconciled.
 - WHERE MEASURES/METRICS ARE DECLARED. consumption-layer-generates-itself: DAB declares measures ('everything a consumption model needs is already declared'; the walk 'inherits the keys and measures of everything it reaches'). rise-of-model-driven: metrics are a DAR declaration ('MRR equals sum of monthly_value for active subscriptions... grain of monthly'). definitions-for-integration demands Definitions for metrics but its four-level hierarchy has no metric level. Three placements.
 - DIRECT DAB QUERYING. Blueprint (absolute): 'Data usage for analytical purposes is only allowed from the DAR layer', because direct DAB usage 'create[s] implicit dependencies that make the system harder to change'. daana-cli-0-7-0 casually contemplates the forbidden practice: 'If you query DAB directly from BI, plan a window accordingly.'
 - NAMING ENFORCEMENT. context-isnt-enough: 'Naming is uniform because it is generated' — there is nothing left to police. stop-being-naming-convention-police: build a CI agent that fetches a Confluence/Notion convention page and enforces it on every PR. That page is a second documentation surface, which context-isnt-enough and work-before-the-answer explicitly forbid ('documentation can't drift because it's the same artifact as the code'). Both cannot be the design.
 - MODEL REGISTRY LOCATION. rise-of-model-driven: 'Platforms need model registries storing entity definitions as queryable metadata - not documentation sites, but active systems driving code generation.' daana-cli-0-7-0: 'the source of truth lives in your version-controlled YAML' AND there is a warehouse metadata schema populated at deploy time that the generator reads. Which is authoritative, and which is queryable, is never settled.
 - M:N RELATIONSHIPS. daana-cli 0.7.0 adds first-class M:N support (set-oriented `view_<source>_has_<target>`, fingerprint-based set-change detection, relationship-only mapping tables). consumption-layer-generates-itself says the USS generator refuses to walk m:n edges and reports them as skipped, and that you must 'model around' m:n in DAB. So the DAB tool now supports a construct the DAR generator cannot consume.
 - IDENTIFIERS ALWAYS vs IDFR OPT-IN. context-isnt-enough: 'Every entity gets identifiers from the start.' integration-by-design: 'Treat multi-identifier resolution as opt-in: turn it on only for entities that genuinely have multiple, source-spanning identifiers' — for a single-key entity 'the pipeline should be skipped entirely'. Reconcilable (identity ≠ the multi-identifier pipeline) but easy to misapply, and neither post says how single-key entities get their surrogate key.
 - CONTRACT GRANULARITY. work-before-the-answer: 'a data contract for each source, owned by the data producing product team'. ai-assisted-data-engineering: 'Each contract specifies a single source-to-staging transformation: which raw table to read...' One-per-source vs one-per-table changes the whole DAS directory layout and ownership model.
 - GENERATED SQL: UNIFORM vs RENAMEABLE. integration-by-design says the surrogate key column name is a convention you should 'rename to whatever fits your code standards' and that `_idfr` columns beyond IDFR and KEY are optional/negotiable. context-isnt-enough says naming and structure are uniform precisely because they are generated and that per-entity variation destroys agent legibility. A configurable generator and a uniform platform pull against each other.
 - DEBUGGABILITY vs GENERATION. work-before-the-answer resolves the black-box objection with 'The business logic is still fully visible, the transformations are still there, you just don't need to write the boilerplate code' and rise-of-model-driven requires generated SQL to stay readable and traceable. But the corpus also insists generated SQL is disposable artifact you never read or edit, and daana-cli 0.7.0's generated pipeline SQL is regenerated per execute and cached for speed. Whether generated SQL is a reviewed surface is unresolved.
 - TWO CODE-GENERATION CHAINS, NEVER RECONCILED. ai-assisted-data-engineering describes both 'A Python generator reads these contracts and produces SQLX files that Dataform executes against BigQuery' and 'YAML contracts fed a compiler producing JSON, which fed a calculation engine generating SQL for BigQuery' — and never says whether these are the same pipeline, or one for DAS staging and one for DAB mappings.
 - AGENT AUTONOMY. designing-for-agentic-experience prescribes progressive trust: tight oversight → documented process + spot checks → independent specialized agents. ai-assisted-data-engineering describes agents already running mandatory protocols and refusing to skip tests. meet-peiman offers 'fully autonomous agents that can build your whole stack with super high quality just by asking the business people questions' as a hot take. The corpus spans manual walkthroughs to full autonomy with no stated criterion for graduation.
 - DEFINITIONS: MACHINE-ACCESSIBLE vs FREE TEXT. definitions-for-integration requires Definitions at four levels (Concept, Characteristic, Domain, Value) plus relationships and metrics, all 'accessible to both humans and AI systems'. DMDL provides only free-text `definition` and `description` strings on entities, attributes and relationships — no Domain object, no per-Value definitions, no allowed-values key (enum vocabularies are carried as prose inside description strings), no acceptance-scope field. The required model and the shown model do not match.
 - 'NO REUSE BETWEEN REQUIREMENTS' vs 'LOGIC DEFINED ONCE'. Blueprint DAR forbids shared structures across user groups; context-isnt-enough says 'Logic is defined once and compiled wherever it is needed.' Reconcilable if 'logic is shared, structures are duplicated' — but no post states that reconciliation, and a builder generating one bridge for everyone will violate the blueprint.
 - BLUEPRINT SAYS NO TECHNOLOGY, THE REST OF THE CORPUS IS TECHNOLOGY. The blueprint insists the overarching document 'contains nothing about technology, processes, modeling methods, or design patterns' and that every tool must be replaceable without invalidating it. Yet the corpus's operative constraints (lowercase framework columns, `ver_tmstp` incremental predicates, IDFR slot counts, the Puppini bridge) are deeply tool-specific. A builder cannot both honour the blueprint's technology-neutrality and follow the concrete guidance.
