GOTCHAS:
  - dataset_name='das__raw' is SILENTLY renamed to 'das_raw' (dlt collapses the double underscore). Only a WARNING log line tells you. Fix: dlt.destinations.filesystem(bucket_url=..., enable_dataset_name_normalization=False). If DAS/DAB/DAR all use double-underscore schema names, every dlt destination in the project needs this flag.
  - DuckDB read_parquet over a glob defaults to the FIRST file's schema and silently drops columns present only in later files — no error, no warning, just missing data. In an append-only lake where you may add a provenance column, always pass union_by_name => true.
  - max_table_nesting=0 is NOT the answer to 'do not normalise'. It only stops child tables; top-level keys still become snake_cased typed columns. Only the payload+data_type='json' hint (or pre-serialising with json.dumps) gives one column.
  - dlt's `json` data_type is NOT a parquet JSON logical type. parquet_schema() shows BYTE_ARRAY / UTF8 / StringType() — byte-identical to a text column. Anything downstream reading the parquet sees a VARCHAR, so the strict layer must cast, always.
  - _dlt_id is regenerated per load. The same source record has a different _dlt_id in every run (10248 was b6aVmzfAxRVPDA then z8O+0F4oaJbS5A). Never use it as a business or record key — add your own content hash.
  - _dlt_loads, _dlt_pipeline_state and _dlt_version are written as .jsonl even when loader_file_format='parquet'. To get a load's completion timestamp you must read_json_auto() the JSONL, not read_parquet(). Better: put das_extracted_at on every row so das__staged never needs that join.
  - dlt inferred freight as DOUBLE when it normalised the record (approach C). Money silently becomes floating point. The strict layer casting to DECIMAL(18,4) out of the JSON string is the fix — another reason not to let dlt infer.
  - Schema evolution is real and late: ship_region only appeared as a column AFTER the first records that had it null, and it landed at the END of the column list. Column ORDER in the parquet is not stable across loads — never rely on positional access.
  - Filesystem `layout` placeholders are arrow-style tokens ({YYYY}, {MM}, {DD}, {load_id}, {file_id}, {ext}, {table_name}, {schema_name}, {curr_date}) — {year}/{month}/{day} raise InvalidFilesystemLayout. The exception text conveniently lists the full valid set.
  - Relative paths inside a DuckDB view's read_parquet() resolve against the DuckDB process's cwd at QUERY time, not at CREATE VIEW time. A view created from the pipeline directory will break when marimo opens the same warehouse.duckdb from elsewhere. Use absolute paths, or a DuckDB variable/macro for the lake root.
  - Two identical runs produce 240 rows for 120 distinct orders. Append-only is correct for DAS but das__staged as written duplicates rows — a dedup/latest-version step (QUALIFY ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY das_extracted_at DESC)) is needed before DAB consumes it.

OPEN:
  - Deduplication strategy between das__raw and das__staged was NOT designed or tested. Two runs gave 240 rows / 120 distinct orders. Does DAB want the full append history, or a latest-version view? This changes whether das__staged is a plain cast view or a QUALIFY/ROW_NUMBER view.
  - Whether enable_dataset_name_normalization=False also disables TABLE name normalisation was not tested — every table name I used was already snake_case. If a source entity is named 'OrderDetails' it may still normalise to 'order_details'; verify before relying on literal names.
  - Not tested: whether DuckDB views over the parquet glob can live inside the SAME warehouse.duckdb that daana-cli installs into, and whether daana-cli's `install`/`deploy` tolerates extra user-created schemas (das__raw, das__staged) in that file.
  - Not tested at scale: 120 rows only. Memory/throughput behaviour with the full 830 Orders (or a large entity) and the cost of DuckDB scanning hundreds of small per-load parquet files was not measured. Small-file accumulation is the obvious risk of one file per load per table.
  - Not tested: incremental extraction (dlt's `dlt.sources.incremental`) against OData — I paginated manually. Whether a cursor on OrderDate/ModifiedDate coexists cleanly with the opaque single-JSON-column design is unverified.
  - Not tested: reading the parquet lake through DuckDB from a remote/object-store bucket_url (httpfs/s3fs). Only local filesystem was exercised, even though s3fs 2026.7.0 was installed.
  - Not tested: what happens when the OData API returns a non-200 or a malformed page mid-pagination — whether the load package is marked failed and whether partial pages are left in the lake.

GOTCHAS:
  - THE BIG ONE — never use `ingestion_strategy: FULL` against a das__staged view that can hold more than one row per primary key. Each execute silently inserts one extra duplicate row into <entity>_desc (22 -> 23 -> 24 -> 25 across three runs in my test), forever, and NONE of the presentation views show it: view_CUSTOMER stayed at 3 rows and view_CUSTOMER_hist at 4 rows the whole time. Since the DAS design is dlt landing parquet, an append/merge write disposition makes das__staged append-style by construction. Use FULL_LOG as the default; reserve FULL for views you can prove are exactly one row per key (dlt `replace` disposition). Switching back to FULL_LOG stops the bleeding but does NOT clean up rows already leaked — you must truncate <entity>_desc and re-execute.
  - ANY other open connection to the .duckdb file makes `daana-cli execute` fail, INCLUDING a read-only one, and the error message is a lie: 'daana framework is not installed on the remote database. Run daana-cli install first...'. The real DuckDB lock error is swallowed and does not appear even at --log-level debug. In this architecture the marimo app reading dar__uss, a dlt pipeline, or a stray `duckdb` REPL will all trigger it. The build needs an explicit single-writer discipline (a lock file, or a supervisor that stops readers before running the DAB step), and whoever operates it must be told that this error means 'the file is busy', not 'run install'.
  - Object names on DuckDB PRESERVE the model.yaml entity-id casing: view_CUSTOMER, CUSTOMER_focal, ORDER_CUSTOMER_x — not the lowercase view_customer PostgreSQL produced. Any DAR/USS generator that hardcodes lowercase names from the PG run will still work (DuckDB resolves case-insensitively, verified all four of view_customer / VIEW_CUSTOMER / "view_CUSTOMER" / "view_customer"), but code that string-matches names out of information_schema WILL break. Either lowercase model.yaml entity ids, or normalize when reading the catalog.
  - <entity>_focal and <entity>_idfr are created but stay EMPTY on DuckDB (0 rows for both CUSTOMER and ORDER) even though execute reports the 'execute_idfr_pipelines' phase as succeeding. All data is in <entity>_desc + <src>_<tgt>_x. If the DAR/USS generator was designed against the PostgreSQL run and joins to _focal or _idfr, it will produce empty results on DuckDB. Build DAR on the view_* layer only.
  - The presentation views are `SELECT * FROM dab.f_CUSTOMER()` — DuckDB TABLE MACROS. Macros do NOT appear in information_schema.tables or information_schema.routines-style catalog queries you might write by habit; you need duckdb_functions(). Any 'is DAB deployed?' health check that only looks at information_schema.tables will see the views but miss the macros they depend on.
  - view_<entity>_with_rel carries NO relationship key columns — its column list is byte-identical to view_<entity>. The name suggests it denormalizes the foreign keys; it does not. Get relationship keys from view_<src>_<rel>_<tgt> (ORDER_key, CUSTOMER_key, type_key, eff_tmstp, ver_tmstp).
  - Every numeric attribute comes back as DECIMAL(28,8) regardless of source type (my DECIMAL(12,2) became 220.25000000). marimo/plotting code downstream should format explicitly rather than trusting the source scale.
  - `daana-cli version` is not a command (Error: unknown command "version"). The version flag is `-v` / `--version`. Trivial, but it will waste a minute in CI.
  - The daana-cli --help text lists 'Multi-database support (PostgreSQL, BigQuery, Snowflake, Oracle, SQL Server)' — DuckDB is NOT advertised. It works fully, but this is unadvertised/possibly-untested territory, which is consistent with the FULL duplication bug and the empty _focal/_idfr tables. Do not expect DuckDB parity to be maintained by the vendor.
  - deploy is re-runnable after editing a mapping (I changed ingestion_strategy and re-deployed four times, always exit 0). execute is re-runnable and idempotent under FULL_LOG and under TRANSACTIONAL, and only non-idempotent under FULL-on-multi-row-source.

If PG populates them, this is a DuckDB-specific defect worth reporting to the vendor and worth guarding in the DAR generator; if PG is also empty, they are simply vestigial and DAR should ignore them.
  - What FULL vs FULL_LOG do on a DELETE — i.e. a key that disappears from the das__staged view on a later load. I ran out of time-box before testing this. This is the remaining strategy difference the build depends on: does FULL tombstone/close the row (row_st flips from 'Y'), or does the entity stay in view_<entity> forever? The _desc table has row_st, sta_tmstp and end_tmstp columns that are all currently 'Y'/NULL/NULL, so the machinery for it exists — but I did not exercise it.
  - Whether the FULL duplication is triggered specifically by multiple rows per primary key, or by the mid-stream switch from FULL_LOG to FULL. I inferred the former because the duplicate appeared only on attributes sourced from the multi-row customers view (type_key 11) and never on the single-row loyalty view (type_key 8, also FULL), and because it recurred +1 per run long after the strategy switch. I did not run a clean FULL-from-scratch-on-a-multi-row-view test to prove it.

  - Whether concurrent daana-cli invocations (two entities in parallel) would deadlock. The 'bounded parallelism' in the help text is intra-process; I did not test two daana-cli processes at once, but given that even a read-only holder breaks it, they will almost certainly conflict.
